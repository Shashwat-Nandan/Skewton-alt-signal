## Executive Summary

**Overall health: B−.** The system that actually trades real money (pair_trading
+ run_paper_pairs) is in genuinely strong shape — production-grade order
lifecycle, incident-annotated tests, hash-pinned deps, clean auth — but the
grade is dragged down by a latent Critical in the *other* strategies' live
paths, an active every-morning live blind window, and a CI that verifies
nothing about code. Top 3 risks: (1) the live pair runner enters its tick loop
~09:19, four minutes after open, because every strategy re-reads 519 bhavcopy
CSVs at startup — open positions are unmanaged through the gap window, and it
worsens daily; (2) Taleb and arbitrage `_live_execute` book PENDING and even
REJECTED orders as filled (known C1, still on main), reachable because the host
already arms `ALLOW_LIVE_MODE=true` and the dashboard's RunManager bypasses
every runner-side risk control; (3) a PR touching live-money code triggers zero
CI, and `redeploy.sh` never installs Python deps, so a dep bump crashes the
timer-driven runners at the next market open. Top 3 opportunities: a pytest+
build CI job (the secret-free conftest already makes this trivial); a single
shared order executor grown from `validate_order` + pair_trading's lifecycle,
killing the three-way live-path fork; and tick-capture retention/compression
before disk math forces the trading-halt path.

## Repo Map

**Purpose.** Solo-operator automated trading of Indian derivatives (Zerodha
Kite) built on Taleb's *Dynamic Hedging* plus a Karpathy-style autoresearch
loop for weekly parameter tuning. One strategy (pair_trading, persistent
runner) trades **real money since 2026-06-08**; the rest are paper/signals.

**Stack.** Python 3.11 (FastAPI + Starlette + uvicorn backend; numpy/pandas/
scipy/statsmodels; kiteconnect), React 18 + Vite + TS SPA, SQLite (WAL),
systemd + nginx on a VPS (dashboard.propelytics.in). ~24k source LOC + ~13k
test LOC, 166 commits, 235 tracked files.

**Architecture sketch.** Two parallel systems sharing strategy code and
filesystem caches, no shared process state:
1. **Headless systemd runners** — `runners/run_paper.py` (Taleb daily), `runners/run_paper_pairs.py`
   (pairs, baseline + persistent + **live**), `runners/run_paper_arbitrage.py`,
   `runners/run_equity_swing.py`; ~30 units/timers in `deploy/`; TOTP auth (`core/kite_auth.py`).
2. **Dashboard** — `backend/main.py` (FastAPI, session-auth, 9 routers) +
   `backend/run_manager.py` (in-process strategy ticks) + `frontend/`; Kite OAuth.

Strategies live in `strategies/` behind `BaseStrategy` + the `STRATEGIES`
registry (`strategies/__init__.py`) — the one clean, enforced boundary.
Backtest harnesses (`backtest*.py`) replay the *real* strategy classes against
per-harness Kite mocks. Autoresearch (`runners/run_autoresearch.py`,
`runners/autoresearch_loop.py`) regenerates `best_params.json` weekly; only Taleb
consumes it.

**Key directories.**
| Path | What it is |
| --- | --- |
| `strategies/` | 4 strategies + helpers; taleb_karpathy.py (2,457 ln) and pair_trading.py (1,880 ln) are god-files |
| `runners/run_paper_pairs.py` | 1,792-ln god-module: live runner + shared scaffolding lib + quant lib + CLI |
| `backend/` | FastAPI app, SQLite layer, OAuth, RunManager (a second, unguarded execution engine) |
| `deploy/` | systemd units, redeploy.sh, smoke.sh, layered Telegram/healthchecks alerting |
| `tests/` | 35 files, incident-annotated, secret-free via conftest |
| `data_cache/` | 29 GB: regenerable caches **and** sole local record of open live positions, mixed |
| `tasks/`, `docs/` | Improvement plans, runbooks, architecture doc (stale — see F-D3) |

**Surprises.** (1) CI is a single lockfile-drift check — nothing else runs on
PRs. (2) `data_cache/ticks/` is 24 GB of the 29 GB with no retention anywhere.
(3) The README's headline safety claim ("dashboard **never** trades live") is
no longer unconditional in code. (4) The live-money engine is named
`runners/run_paper_pairs.py`.

## Audit Report

### Critical

**C-1 ◆ Taleb (and arbitrage) live execution books phantom fills — including for orders never placed.** [FACT]
`strategies/taleb_karpathy.py:2440-2457` `_live_execute` places a LIMIT order
and returns `status="PENDING"` with no fill polling; pre-submit validation
failure returns `REJECTED`. `execute_proposals` at `taleb_karpathy.py:1554-1558`
skips state mutation **only** on `FAILED` — so PENDING and REJECTED both deduct
costs, append positions, and book realized P&L at proposal price.
`strategies/arbitrage.py:1072-1094` has the same shape. pair_trading fixed
exactly this on 2026-05-21 with a COMPLETE-whitelist + poll-until-terminal
(`pair_trading.py:509-530, 1586-1864`); the fix never propagated. No test
touches taleb `_live_execute` (zero grep hits in the 3,021-ln suite; only the
FAILED branch is covered). This is the known C1 from
`tasks/improvement-plan-2026-05-29.md`, still unfixed. Today it is gated
(`runners/run_paper.py:321-323` forces paper; `backend/settings.py:53` defaults False)
— but the host `.env` arms `ALLOW_LIVE_MODE=true` for the live pair runner,
which also arms the dashboard's gate (`backend/routers/runs.py:55`), and the
dashboard can construct a Taleb run. One UI action away from a live path that
diverges book state from broker on the first unfilled order.
*Three agents converged on this independently.*

### High

**H-1 Live pair runner is blind for the first ~4 minutes of every session, worsening daily.** [FACT]
Every `PairTradingStrategy.__init__` calls `_seed_spread_history` →
`screen_pairs.load_front_month_panel`, re-reading all 519 bhavcopy CSVs
(3.4 GB) per strategy with no shared cache (`strategies/pair_trading.py:
1489-1516`, `core/screen_pairs.py:75-97`, builder loop `runners/run_paper_pairs.py:595-649`).
Today's live log: start 09:12:23, five "Reading 519 bhavcopy files" passes,
"Entering tick loop" at **09:19:07**. Stop-z/exit checks don't run 09:15–09:19;
an adverse open gap on a held live pair is unmanaged. Grows ~1 file/day.

**H-2 ◆ The dashboard's RunManager is a second execution engine that bypasses every runner-side risk control.** [FACT placement / JUDGMENT scenario]
HALT flags (`runners/run_paper_pairs.py:63-64, 654-675`), daily-loss auto-halt (:847),
Kite throttle (:1537), broker reconcile (:1150), state persistence + backups,
and the flock single-instance lock (:924) are all runner-side.
`backend/run_manager.py:163-226` ticks the same strategy classes with none of
them; its only gate is `allow_live_mode` (`backend/routers/runs.py:55`) — which
the host has armed. Even paper runs are mutually invisible between dashboard
and systemd.

## Improvement Strategy

Four themes explain ~90 % of the findings:

**Theme 1 — Safety was built where the pain was, and nowhere else.**
Every hard lesson (phantom fills, partial legs, halt flags, reconcile, locks)
got encoded into pair_trading/run_paper_pairs — and only there. C-1, H-2, H-6,
M-1, M-2 are all "the fix never propagated." *Target state:* one shared order
executor (grown from `validate_order` + the pair lifecycle) and one shared
runner-scaffolding module, so a lesson learned once is enforced everywhere.
*Principle:* in a real-money system, safety code must be impossible to opt out
of by being in the wrong file.

**Theme 2 — Nothing guards the gate between "paper repo" and "live money".**
CI runs nothing (H-3), the live quad-lock is untested (H-5), redeploy skips dep
install (H-4), the README misstates the live gate (H-9), the dashboard engine
bypasses runner controls (H-2). *Target state:* every PR runs tests + build;
the live-arming surface is pinned by tests using the exact service-file argv;
the dashboard's live refusal is unconditional again. *Principle:* the cost of
a green-but-wrong merge is now denominated in rupees, not minutes.

**Theme 3 — Unbounded operational growth with no retention story.**
24 GB ticks (H-8), startup cost growing 1 file/day until it blinded the live
open (H-1), state/log/db growth (Lows). *Target state:* a written retention
policy implemented in `deploy/` (compress + archive ticks, prune derived
caches), and startup work made O(1) per session. *Principle:* a persistent
trading system's resource curves must be flat or have a dated cliff someone
chose.

**Theme 4 — Configuration and docs trail the system's actual state.**
Four config mechanisms with known clobber incidents (H-7), stale architecture/
README/VPS docs (H-9, M-11). *Target state:* one "effective params" dump logged
at every runner startup (making drift observable), a tracked-file-safe
autoresearch regen, and docs that lead with what can move money. *Principle:*
the docs' job is to stop the operator (or an agent) from acting on a wrong
model of the system.

**Explicitly NOT recommending:**
- Splitting the strategy god-files into many modules now (M-2). The blast
  radius of a big refactor on a live system exceeds the payoff; extract only
  the execution/accounting seam (where C-1 lives) and stop.
- Unifying the three backtest mocks into one framework (M-7). Note the
  divergence, share `_max_drawdown`, move on — tuning currently feeds only a
  paper strategy.
- Frontend test infrastructure, mypy adoption, or microservice-style
  separation of dashboard/runners. Solo-operator maturity doesn't justify it;
  ruff + tsc-in-CI gets 80 % of the value.
- Fixing M-4 (STT rates) before independently verifying current NSE/SEBI rates
  — wrong-direction "fix" is worse than the known bias.

**Definition of done (measurable):**
- CI fails on test failure, ruff error, or frontend build error for every PR.
- Zero Critical findings: taleb/arbitrage live paths either share the
  COMPLETE-whitelist executor or hard-refuse live mode; a test pins it.
- Live runner log shows "Entering tick loop" ≤ 09:15:30 IST.
- `df` trend on the VPS flat month-over-month (ticks compressed/archived).
- Healthchecks.io shows a daily *success* ping (dead-man's switch live).
- A characterization test runs `run_paper_pairs.main()` with the exact
  live-service argv against a stub Kite.
- `git status` clean on the production host after a full autoresearch cycle.
